# Описание

Хельхейм реализует комплексное ПО для односторонней синхронизации файловой структуры в формате `master -> slave`.

Он представляет собой 2 программы-демона:

- `master` - программа отправитель файлов. Занимается мониторингом файловой структуры, и в случае выявления изменений
  отправляет в `slave` файлы и их событиях
- `slave` - программа получатель файлов. Является слушателем, который принимает информацию от `master` о файлах и
  повторяет события

Под событиями подразумевается `Создание`, `Изменение содержимого` и `Удаление`.

# Features

- При первом запуске `master` сверяет свою файловую структуру с `slave` и синхронизирует только то, что отличается.
  Файлы в `slave`, отсутствующие в `master`, будут удалены.
- `master` рассчитан на нестабильную работу сети, и при восстановлении соединения с `slave` самостоятельно продолжает
  синхронизацию
- `slave` рассчитан на нестабильную работу сети, поэтому при получении новых и/или измененных файлов создает временный
  файл, в который складывается содержимое. Только после получения финального чанка происходит создание/замена файла.
- Реализована **защита от MITM**. Во время передачи чанков `slave` сравнивает HashSum чанка, которую вычислил `master`,
  с тем, что получил. После получения финального чанка происходит дополнительная сверка HashSum файла.
- Единственным признаком изменения файла служит **изменение HashSum его содержимого**. Это позволяет избежать ошибок,
  когда файловая система позволяет изменить файл не меняя его timestamp.
- Учитывается, что могут быть файлы с нулевым размером (к примеру `.gitkeep`). Они также подлежат синхронизации.
- Процедура полного вычисления HashSum содержимого файла оптимизирована и ей необходим `1MB` оперативной памяти вне
  зависимости от размера файла.
- Рассчитан на условия ресурсного голода. В зависимости от размера файловой структуры `master` для полноценной работы
  потребляет до `5MB` оперативной памяти, `slave` - до `10MB`

# Запуск

Возможен как [ручной запуск](#ручной-запуск), так и [запуск через docker compose](#запуск-через-docker-compose)

## Ручной запуск

Для самостоятельного запуска необходимо произвести билд приложений

```bash
cd app
go build -o master cmd/master/main.go
go build -o slave cmd/slave/main.go
```

### Запуск `master`

```bash
./master -dir=/dir/source -interval=30 -chunkSize=5 -addr=127.0.0.1:50051 -vv
```

Описание флагов:

- `dir` - директория, которая подлежит сканированию
- `interval` - длительность перерыва между повторным сканированием структуры в секундах
- `chunkSize` - размер чанка в МБ при отправке в `slave`
- `addr` - адрес получателя (gRPC server) в формате "HOST:PORT"
- `vv` - включение режима полного дебага

### Запуск `slave`

```bash
./slave -dir=/dir/dest -chunkSize=5 -port=50051 -vv
```

Описание флагов:

- `dir` - директория, которая подлежит синхронизации
- `chunkSize` - максимальный размер чанков от `master` в МБ (gRPC серверу выделяется +5МБ)
- `port` - порт gRPC сервера
- `vv` - включение режима полного дебага

### Сбор логов

Для сбора логов о критических ошибках можно `> /var/my-logs.txt`. Не рекомендуется включать режим полного дебага в
продуктовой среде.

## Запуск через `docker compose`

Скопируйте и внесите изменения в `.env.example`

```bash
cp .env.example .env
```

Запустите нужный вам контейнер

```bash
docker compose up -d master
docker compose up -d slave
```

Описание флагов смотри в ["ручной запуск"](#ручной-запуск)

### Сбор логов

Для сбора логов о критических ошибках можно использовать вывод логов контейнеров.

```bash
docker compose logs master
docker compose logs slave
```

Не рекомендуется включать режим полного дебага в продуктовой среде.
